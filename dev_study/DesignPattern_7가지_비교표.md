# 디자인 패턴 7종 통합 비교표

| | Strategy | Factory | Adapter | Decorator | Observer | Template Method | Repository |
|---|---|---|---|---|---|---|---|
| **한 줄 요약** | 알고리즘을 갈아 끼운다 | 생성 규칙을 한곳에 모은다 | 안 맞는 인터페이스를 끼워 맞춘다 | 기능을 겹겹이 덧씌운다 | 상태 변화를 구독자에게 알린다 | 골격은 고정, 내용만 각자 채운다 | 데이터 접근을 전담 사서에게 맡긴다 |
| **분류** | 행위 (Behavioral) | 생성 (Creational) | 구조 (Structural) | 구조 (Structural) | 행위 (Behavioral) | 행위 (Behavioral) | 실무 필수 |
| **비유** | 같은 주방, 다른 조리법 | 안내 데스크 | 여행용 돼지코 | 선물 포장 | 유튜브 구독 | 도시락 공장 | 도서관 사서 |
| **해결하는 문제** | 같은 목적의 처리 방식이 여러 개이고 `if/elif`가 계속 늘어남 | 조건에 따라 다른 객체를 만드는 `if/elif`가 여기저기 흩어져 있음 | 외부 SDK·레거시 모듈의 인터페이스가 우리 표준과 다름 | 재시도·로깅·캐싱 같은 부가 기능을 여러 함수에 복붙하고 있음 | 하나의 사건에 후속 처리가 여러 개고 계속 늘어남 | 여러 작업이 같은 순서를 따르는데 뼈대가 복붙되고 있음 | 비즈니스 로직 안에 SQL이 섞여서 테스트·DB 교체가 어려움 |
| **핵심 메커니즘** | 조합 (주입) | 딕셔너리 레지스트리 | 래핑 (감싸기) | 래핑 (감싸기) | 구독/발행 | 상속 | 인터페이스 + 구현 분리 |
| **런타임 교체** | 가능 | 해당 없음 (생성 시 1회) | 가능 | 가능 (조합 변경) | 가능 (구독/해제) | 불가 (상속 고정) | 가능 |
| **장점** | 새 정책 추가 시 기존 코드 수정 없음. 각 정책 개별 테스트 가능 | 생성 규칙이 한 곳에 모임. 호출부는 구체 클래스를 몰라도 됨 | 외부 시스템 교체 시 어댑터만 변경. 외부 규약이 내부로 퍼지지 않음 | 원래 함수 수정 없이 부가 기능 추가. `@` 한 줄로 재사용 | 후속 처리 추가 시 발행자 코드 수정 없음. 느슨한 결합 | 공통 뼈대가 한 곳에만 존재. 순서 실수 방지 | DB 없이 테스트 가능. SQL 한곳 관리. DB 교체 용이 |
| **단점** | 정책 수가 적으면 과설계. 정책 목록 한눈에 보기 어려움 | Factory가 거대해지면 문제를 옮긴 것뿐. 단순할 때 불필요한 계층 | 어댑터 클래스가 계속 늘어남 | 3개 이상 쌓으면 실행 순서 파악 어려움. 콜스택 깊어짐 | 디버깅 어려움. 구독자 실패 시 연쇄 영향. 메모리 누수 위험 | 상속 기반이라 유연성 낮음. 계층 깊어지면 이해 어려움 | 단순 CRUD에는 과설계. 인터페이스+구현체 두 벌 관리 |
| **풀무원 적용 예시** | 배송비 정책 (일반/VIP/이벤트) | 채널별 주문 파서 (쿠팡/네이버/컬리) | SMS 업체 SDK, 레거시 ERP 메일 모듈 연동 | API 호출에 재시도·소요시간 로깅 | 주문 출고 시 알림톡·재고차감·정산 | 일별 배치 (매출집계/재고스냅샷) | 주문 조회·저장 (Oracle → Snowflake 전환 대비) |
| **쓸 때** | 정책이 3개 이상, 자주 바뀜 | 만들 종류가 3개 이상, 계속 늘어남 | 못 고치는 외부 시스템과 연동 | 같은 부가 기능을 여러 함수에 붙여야 함 | 후속 처리가 3개 이상 | 같은 절차의 작업이 3개 이상 | 로직이 복잡하고 테스트가 중요할 때 |
| **쓰지 말 때** | 분기 2개, 고정적 | 만들 객체 1~2종, 고정적 | 인터페이스가 이미 같을 때 | 한 함수에만 필요할 때 | 후속 처리 1~2개, 고정적 | 하위 클래스 1~2개뿐일 때 | 단순 스크립트, 일회성 배치 |

## 1. Strategy (전략)

| 항목 | 내용 |
|---|---|
| **한 줄 요약** | 알고리즘을 갈아 끼운다 |
| **해결하는 문제** | 같은 목적의 처리 방식이 여러 개이고 `if/elif`가 계속 늘어남 |
| **비유** | 같은 주방, 다른 조리법 |
| **장점** | 새 정책 추가 시 기존 코드 수정 없음. 런타임에 방식 교체 가능. 각 정책을 개별 테스트 가능 |
| **단점** | 정책 수가 적으면 클래스만 늘어나서 과설계. 정책 목록을 한눈에 보기 어려움 |
| **쓸 때** | 배송비·할인·수수료 등 정책이 3개 이상이고 자주 바뀔 때 |
| **쓰지 말 때** | 분기가 2개이고 앞으로도 안 늘어날 때. 파이썬에서는 함수 하나로 충분할 때 |

---

## 2. Factory (팩토리)

| 항목 | 내용 |
|---|---|
| **한 줄 요약** | 생성 규칙을 한곳에 모은다 |
| **해결하는 문제** | 조건에 따라 다른 객체를 만드는 `if/elif`가 여기저기 흩어져 있음 |
| **비유** | 안내 데스크 (맞는 담당자를 불러줌) |
| **장점** | "어떤 걸 만들지"가 한 곳에 모여 채널 추가가 쉬움. 호출부는 구체 클래스를 몰라도 됨 |
| **단점** | Factory 자체가 거대한 분기가 되면 문제를 옮기기만 한 것. 단순한 경우 불필요한 계층 추가 |
| **쓸 때** | 채널별 파서, 메시지 유형별 핸들러 등 종류가 3개 이상이고 계속 늘어날 때 |
| **쓰지 말 때** | 만들 객체가 1~2종이고 고정적일 때 |

---

## 3. Adapter (어댑터)

| 항목 | 내용 |
|---|---|
| **한 줄 요약** | 안 맞는 인터페이스를 끼워 맞춘다 |
| **해결하는 문제** | 외부 SDK·레거시 모듈의 인터페이스가 우리 표준과 다름 |
| **비유** | 여행용 돼지코 (콘센트 변환) |
| **장점** | 외부 시스템 교체 시 어댑터만 바꾸면 됨. 외부의 이상한 규약이 우리 코드에 퍼지지 않음 |
| **단점** | 어댑터 클래스가 하나씩 늘어남. 너무 많은 어댑터는 구조를 복잡하게 만듦 |
| **쓸 때** | 레거시 ERP·물류사 API·PG사 등 우리가 못 고치는 외부 시스템과 연동할 때 |
| **쓰지 말 때** | 외부 인터페이스가 우리 표준과 이미 같을 때. 연동 대상이 하나뿐이고 바뀔 일이 없을 때 |

---

## 4. Decorator (데코레이터)

| 항목 | 내용 |
|---|---|
| **한 줄 요약** | 기능을 겹겹이 덧씌운다 |
| **해결하는 문제** | 재시도·로깅·캐싱 같은 부가 기능을 여러 함수에 복붙하고 있음 |
| **비유** | 선물 포장 (선물은 그대로, 포장지만 추가) |
| **장점** | 원래 함수를 수정하지 않고 부가 기능 추가. 부가 기능이 재사용 가능한 부품이 됨. `@` 한 줄로 적용 |
| **단점** | 3개 이상 쌓으면 실행 순서 파악이 어려움. 디버깅 시 콜스택이 깊어짐 |
| **쓸 때** | 로깅·재시도·인증·캐싱 등 같은 부가 기능을 여러 함수에 붙여야 할 때 |
| **쓰지 말 때** | 부가 기능이 한 함수에만 필요할 때. 데코레이터가 4개 이상 쌓이려 할 때 |

---

## 5. Observer (옵저버)

| 항목 | 내용 |
|---|---|
| **한 줄 요약** | 상태 변화를 구독자에게 알린다 |
| **해결하는 문제** | 하나의 사건(출고 등)에 후속 처리가 여러 개고 계속 늘어남 |
| **비유** | 유튜브 구독 (영상 올리면 구독자에게 알림) |
| **장점** | 후속 처리 추가 시 발행자 코드 수정 없음. 발행자와 구독자가 서로를 모름(느슨한 결합) |
| **단점** | 디버깅 어려움 ("이 함수 누가 호출한 거지?"). 구독자 중 하나가 실패하면 뒤쪽에 영향. 구독 해제 안 하면 메모리 누수 |
| **쓸 때** | 주문 출고·결제 완료 등 하나의 이벤트에 후속 처리가 3개 이상일 때 |
| **쓰지 말 때** | 후속 처리가 1~2개이고 고정적일 때. 실행 순서가 엄격히 보장돼야 할 때 |

---

## 6. Template Method (템플릿 메서드)

| 항목 | 내용 |
|---|---|
| **한 줄 요약** | 골격은 고정, 내용만 각자 채운다 |
| **해결하는 문제** | 여러 작업이 같은 순서(조회→변환→적재)를 따르는데 뼈대가 복붙되고 있음 |
| **비유** | 도시락 공장 (공정 라인은 같고 반찬만 다름) |
| **장점** | 공통 뼈대가 한 곳에만 존재. 뼈대 변경(슬랙 알림 추가 등) 시 한 곳만 수정. 실수로 순서를 바꿀 위험 없음 |
| **단점** | 상속 기반이라 유연성이 낮음(런타임 교체 불가). 상속 계층이 깊어지면 이해가 어려움 |
| **쓸 때** | ETL 배치·리포트 생성 등 절차가 확실히 고정된 작업이 3개 이상 반복될 때 |
| **쓰지 말 때** | 절차 자체가 바뀔 수 있을 때. 하위 클래스가 1~2개뿐일 때 |

---

## 7. Repository (리포지토리)

| 항목 | 내용 |
|---|---|
| **한 줄 요약** | 데이터 접근을 전담 사서에게 맡긴다 |
| **해결하는 문제** | 비즈니스 로직 안에 SQL이 섞여서 테스트·DB 교체가 어려움 |
| **비유** | 도서관 사서 (이용자는 서고 배치를 몰라도 됨) |
| **장점** | DB 없이 비즈니스 로직 테스트 가능. SQL이 한 곳에 모여 관리 용이. DB 교체 시 Repository만 교체 |
| **단점** | 단순 CRUD에는 과설계. Repository 인터페이스와 구현체 두 벌을 관리해야 함 |
| **쓸 때** | 비즈니스 로직이 복잡하고 테스트가 중요한 도메인. DB 교체 가능성이 있을 때 |
| **쓰지 말 때** | 단순한 스크립트나 일회성 배치. 로직 없이 DB 읽고 쓰기만 하는 경우 |

## 패턴 분류 한눈에 보기

| 분류 | 패턴 | 관심사 |
|---|---|---|
| **생성 (Creational)** | Factory | 객체를 **어떻게 만들까** |
| **구조 (Structural)** | Adapter, Decorator | 객체를 **어떻게 조립할까** |
| **행위 (Behavioral)** | Strategy, Observer, Template Method | 객체가 **어떻게 협력할까** |
| **실무 필수** | Repository | **데이터 접근을 어떻게 분리할까** |
