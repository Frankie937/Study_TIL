

# RAG vs LLM wiki 

* 비유 
- RAG: 대학교 오픈북 시험 
- LLM wiki: 시험 전 요약노트를 만들어서 보는 시험 (노트가 책의 원문을 대체하지 않음) 

### 진짜 차이? 
* (1) 비용 시점 
	- RAG: 찾고 조합할 때 비용이 듦 
	- LLM wiki: 자료가 들어오는 순간에 자료를 정리하는 비용이 듦 

* (2)  
	- RAG: 없던 것을 만들어내지 못함 
	- LLM wiki: 원본에 없던 레이어가 하나 생김 

* (3)  
	- RAG: 없다는 것을 모름
	- LLM wiki: 인덱스가 있어서 없다는 것을 앎 

### 선택할 때 고민해야 하는 것들 
- 최신성/ 권한 
- 최신근거를 찾는일을 누가 검토할 지 
- 원본을 바뀌면 정리본을 누가 고칠지 

### RAG 언제 쓸지 언제 안쓸지의 기준은 보통 어떤 질문을 하는 지 봐야 한다. 
* 단순하게는, 
	- RAG: '원문 그대로 보여달라' 는 질문과 요구사항이 많음 ex) 육아휴직 개정된 부분 보여달라 등 
	- LLM wiki: '여러 자료 종합해서 설명해달라'는 질문이 많음 
* 지식의 3갈래
	- 바뀌지 않는 지식
	- 자주 바뀌는 지식
	- 사람이 넣을 때마다 변경되는 지식

### '승격'의 절차 
- 반복해서 가치가 있고, 사람이 승인한 것을 지식으로 두는 것 
- 원문이 사실이라고 해서 모든 게 지식이 되는 것은 아님 

> wiki를 만드는 것은 쉬움. 그것을 잘 운영하고, 유지하는 게 중요 

### wiki를 잘 만들기 위한 단계 
- 1단계 : 질문부터 적기 (성능을 증명하려는게 아니라, 무엇이 필요한지 발견하려는 작업)
- 2단계 : 자료를 한 폴더에 모으고 파일명과 제목을 정리 
- 3단계 : 여러 자료에서 같은 내용을 계속 종합하고 있다면 그때 wiki를 붙이기 
	- 앞에서 적은 질문 목록들 기준으로 shcema.md 만들고, 원본은 딱 하나만 넣어서 원하는대로 나오는 지 확인하기
	- (** shcema.md : ai의 기억 자체를 적는 문서가 아니라, 어떻게 관리할 지 적어두는 문서)

### chroma 회사에서 18개의 모델로 실험해서 확인한 것 
- 입력이 길어질 수록 단순한 문제에서도 정확도가 떨어짐, 관계없는 문서를 딱 하나만 넣어도 성능이 떨어짐을 확인 
	- 많이 넣을 수록 좋아진다는 우리의 가정을 검증해보니 반대로 나온 것

### 정리의 2종류
- 1. 폴더를 주제별로 나오고 파일 제목을 통일하는 것은 사람을 위한 정리 
- 2. AI에게 일을 잘 시키는 것은 "읽을 후보를 줄이는 것" (안봐도 되는 걸 치우는 것 )
	- wiki가 잘 되는 이유도 읽어야 할 후보를 줄여주기 때문	

### 혼자일 때는 모르고 안보이던 문제가 사람이 늘어나는 순간 핵심문제가 됨 
- 500페이지 이하의 문서에서는 굳이 rag를 안붙여도 되고, 그 이상의 문서는 숫자가 아니라 "증상"을 보기 (페이지수는 출발선일 뿐이고, 붙이는 시점은 증상, 실패가 정해줌)
- 그 증상, 실패 란?
	- 파일 검색이 자꾸 놓칠 때 
	- 표현이 달라서 못찾을 때
	- 목차 파일 자체가 너무 커서 뭐가 있는지 보는 파일이 부담스러울 때 

- 개인이라도 법률자료나 건강기록 처럼 틀렸을 때 손해가 큰 경우라면, 회사에서 쓰이는 장치들이 필요 
- 회사로 넘어가면 시작은 항상 비슷함. "우리 회사자료 모두 학습해주세요" 라고 요구힘 
	- 그러나, 정작 무엇을 물어볼 건지, 정확한 답이 중요한지, 시간단축이 중요한지, 쓰는 사람인 여러 부서인지 등 되물으면 정해지지 않은 경우가 많음 
	- 이렇게 요구가 정해지지 않은 채로 자료부터 넣으면 무엇을 만들었는지 아무도 검증할 수 없음 
	
### 예를 들어, 사내 챗봇을 사용해보고 "이거 그냥 검색이 빠를 것 같은데" 라는 생각이 들었다면, 이건 기술이 부족해서가 아니라 다음 3가지 중 하나가 빠진 것 
- 최신근거를 누가 찾을 지 
- 반복되는 설명을 누가 검토할 지
- 원본이 바뀌면 정리본을 누가 고칠 지
	- 개인은 이걸 혼자 다하지만, 회사는 나눠야 하고 개인에게는 없던 항목들이 더 붙음 
		- 1) 무엇이 공식 문서인지 정해야 함
			- 시스템에 먼저 들어온 파일이 공식문서가 아님. 회사에서 공식이라고 이야기한 문서가 따로 있어야 함. 
			- 새 버전이 나왔을 경우에 이전 버전으로 만들어둔 정리본을 누가 고치고 누가 버릴지도 정해야 함 (원본 파일이 하나 지웠다고 해서 정리본에서 자동으로 사라지지 않기 때문에)
		- 2) 볼 수 있는 사람에게만 보여줘야 함 (개인에게는 없던 항목) 
			- 문서의 부서와 보안등급을 적어두는 것만으로 지켜지지 않는다. 그것은 표시일 뿐이기 때문에 실제로 막는 장치가 따로 있어야 함.
			- 그리고 순서가 중요함. 일단 다 찾아온 다음에 답변에서 비밀문서를 빼는 방식은 늦음. (금고를 다 열어놓고 못본 척하는 것과 같음) 권한 없는 문서는 AI가 읽기 전에 걸러져야 함.
		- 3) 누가 검토하고, 누가 고칠 수 있을 지 정해야 함 
			- 일반 직원은 질문하고, 자료를 제출하고 / 관리자가 정리본을 검토하고, 수정하고 / 운영책임자가 규칙 자체를 바꾸는 식이어야 함 
			- 모두가 AI에게 규칙과 기억을 마음대로 바꿀 수 있으면 지식은 관리되는 것이 아니라 흔들림
	- 이건 근데 단순히 정해두는 것만으로 안지켜짐! 절차가 있어야 함!!!
		- 예를 들어, 개인은 자기 작업공간에서 초안을 쓰고, 근거가 된 원본은 정해진 자리에 따로 놓고 이걸 팀 지식으로 올리자는 요청이 들어오면 AI가 먼저 검토한다. 
		- 규칙을 어기지 않았는지, 이미 있는 지식과 부딪히지 않는지, 어디에 두는 게 맞는지 까지도. 그리고 마지막에 사람이 승인해야 팀 지식이 됨 (승격)
		- 개인은 원본을 정리본으로 올릴 지만 정하면 되었음
		- 그러나, 회사는 이러한 승격 절차가 하나 더 있음. 회사는 개인의 지식을 팀의 지식으로 정할 지 정하는 것 
			- 이 추가된 절차가 번거로워보이지만, 그 한 단계를 빼면 그 안은 곧 바로 쓰레기장이 되어버림. 
		- 회사 전체를 wiki 하나로 덮으면 부서마다 같은 용어를 다른 의미로 쓰고 관련없는 지식이 답변에 섞임 
		- 저장소를 여러 개로 쪼개라는 것은 아님. 한 곳에 두되, 질문 하나가 전부를 읽지 못하게 막아야 함
		- 직원 한명을 채용하듯 직무마다 지식 영역을 하나씩 두라고 권함 
		- 질문이 들어오면 시스템이 어느 영역을 읽을지 부터 고르게 함 

###  좋은 AI 기업 시스템은 모든 질문에 혼자 답하는 천재가 아님 
- 해당 질문을 알맞은 담당자에게 넘기는 접수 창구에 가까움 
- 영역을 나눌 때 하나만 같이 정하면 됨 
- '읽는 범위'가 아니라 '쓰는 자리', 자리는 3개면 충분함 
	- 1) 개인이 초안을 쓰는 영역 
	- 2) 팀이 같이 쓰는 영역
	- 3) 어디로도 올라가지 않는 영역 (팀에 공유하고 싶지 않거나, 아직 정리가되지 않은 것) --> 검토 절차에 올라오지도 않음 

- 무엇을 사람이 하고 무엇을 AI에게 맡길지도 여기서 갈림 
	- 지우는 일과 권한을 정하는 일은 사람이 함 (나머지 귀찮은 일은 AI에게 시키기)
	- 회사는 어디서부터 시작하는가?
		- 질문부터 적기! 실제로 쓸 부서에서 5개씩 질문을 받기
		- 요구가 정해져있지 않으면 무엇을 만들었는지 검증할 수 없음
		- 검증기준이 질문 목록이고, 부서별 질문 목록이 부서별 지식 영역의 범위가 됨 


### Recap) 다시 질문, RAG대신 LLM wiki를 쓰면 될까? 
- 개인이라면, 조건이 맞으면 됨 
	- 자료구조를 눈으로 확인할 수 있고, 파일검색만으로 필요한 자료가 빠짐없이 나오고, 같은 설명을 반복하고 있다면 파일기반의 wiki부터 시작해도 좋음 
	- 빠르게 바뀌는 원문을 매번 확인해야 하거나, 표현이 달라서 자료를 놓치면 안되거나, 여러 사람이 동시에 쓰고 권한을 걸려야 한다면 검색을 붙이는 편이 좋음 
- 회사라면, 둘 중 하나를 고르는 질문 자체가 부족함 
	- 찾는 일과 정리하는 일을 각각 어디서 책임질지 정하는 게 먼저. 
	- 자료를 모으는 일은 지금 시대에는 AI 덕분에 거의 공짜가 됨. 그렇기 때문에 중요한건 반대로, "무엇을 안넣을 것인가"를 잘 결정해야 함

> 정리본은 만드는 순간 원문에 없던 문장을 만듦
> 좋은 자료만 들어가면 원문 어디에도 없던 인사이트가 생기고, 나쁜 자료가 섞이면 원문 어디에도 없던 헛소리가 생김.

- 시스템이 틀린 게 아니라, 안지운 것들이 새 지식에 안좋은 재료가 되어버림. 

>  좋은 지식 베이스는 많이 쌓인 게 아님, 안좋은 게 안들어간 것 !!!
